# Positioning

## Line

Forward deployed engineer who lands AI and data systems inside a customer's cloud, then stays until the workflow changes.

## What is already true

Seven years of production cloud work: GCP, GKE, Terraform, CI/CD, SRE, and MLOps. That is the advantage over a new-grad FDE profile. You can deploy into someone else's VPC, talk about IAM and rollback, and stay for the week after the demo.

## What the profile still has to prove

| FDE signal | Evidence a reviewer can open |
| --- | --- |
| Discovery | A brief that names the user, the sponsor, and one constraint that changed the design |
| Judgment | A design doc that rejects the impressive option and says why |
| Customer systems | An integration over messy exports, not a clean public API |
| Safety | An explicit rule for what data may leave, and an audit log that follows it |
| Measurement | An eval or a timed workflow with a number agreed before the build |
| Communication | A readout written to the operator, not to other engineers |
| Handoff | A rollback that does not depend on you being online |

## Who this is for

Deployed and forward deployed roles where the product has to run in the customer's environment:

- Palantir-style deployed engineering
- Applied AI and model-deployment teams that embed with customers
- Data and cloud companies that send engineers, not slide decks

Solutions engineering that stops at a demo is a different job. The portfolio should show code that survives their security review.

## How to talk about the existing portfolio

Do not throw away the SRE and MLOps work. Point at it as the production half of the story:

- GCP, GKE, and Terraform show you can land the system in their project.
- SLOs, incident response, and runbooks show you stay after go-live.
- The FDE repos show you can choose the problem and explain it to the buyer.

Headline shape: `Forward Deployed Engineer | GCP, Kubernetes, production ML systems`.
